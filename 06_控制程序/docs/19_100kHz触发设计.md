# 19 100 kHz 触发：设计记录和要问 Rui 的

> 2026-10-15 记。来源：用户转述的 Rui 10/15 要求 + 本会话（67ed74c7）的讨论。数字都是按代码和已知参数算出来的 [条件计算]，**代码还没写**（bscan_test_100k.m 待用户同意后写）。
> 相关：bscan_test.m（现在的"每 K 步一个触发"写法）、docs/12（DMA）、docs/13（B-scan 记录）、docs/17 §4（改触发频率的规则）、Rui Phase 1 计划第 30 行。

## 1 Rui 10/15 说的（用户转述，不是转录）
- 代码要能在 **100 kHz** 下运行：用激光时就是这个频率；现在用函数发生器测也可以。
- 匀速扫和走–停–采（step-and-settle）**是一样的**：画时序图的话，只是时间轴上 t 的长短不同。

## 2 现在的程序为什么跑不了 100 kHz
- bscan_test.m 每走 K 步发一个触发，一个位置一条 A-line，所以 **扫描速度 = DX_UM × TRIG_RATE_HZ ≤ 4 mm/s**（第 37 行），即 TRIG_RATE_HZ ≤ 4000 / DX_UM。
- 10/15 实际碰到：TRIG_RATE_HZ = 100e3、DX = 5 µm → 500 mm/s → 第 60 行 assert。
- 100 kHz 要 DX = 0.04 µm，比一步 0.5 µm 还小，这种写法做不到。要把**触发和电机走步分开**。

## 3 100 kHz 时的关键关系 [条件计算，100 kHz、4 mm/s]
- 每走 1 µm 有 25 条 A-line；每个像素的条数 **N = 频率 × 像素间距 ÷ 速度**：像素 5 µm → N = 125；1 µm → N = 25。
- 一行 3 mm 用 0.75 s，产生 75,000 条 A-line，约 150 MB（每条 1024 点 × 2 B）。A-line 条数由时间决定，和像素设多大无关。

## 4 Rui 说的"一样"：时序图上就是这样
```
匀速扫：STEP 均匀，TRIG 均匀，同时进行
STEP  _|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_ ...   每 125 µs 一步（8 kHz）
TRIG  ||||||||||||||||||||||||||||||||| ...   每 10 µs 一发（100 kHz）

Step-and-settle：走 → 停 → 打，轮流
STEP  _|‾|_|‾|_ …(K 步)____________________________ _|‾|_ …
TRIG  ________________________ (停稳) ||||| (N 发) ____ ____ …
```
- 两种都是同一张表的两种排法：**每个像素停多久 = 0** 就是匀速扫，> 0 就是 step-and-settle。
- 所以代码写成一个通用的时序表生成器，用三个参数描述一个像素：每个像素走几步（K = 像素间距 ÷ 0.5 µm）、每个像素停多久、触发频率（固定 100 kHz）。两种方式都能跑，切换只改一个数。

**时序图上看不出、要实测的三件事**（不是两种方式本质不同，而是真实台架上会怎样）：
1. 打这一发时滑台在不在动：匀速扫两发之间只走 4 mm/s × 10 µs = 0.04 µm，远小于一步（0.5 µm）和分辨率（约 1 µm），像素不比分辨率大时基本可以忽略。
2. 停下来会不会晃：每次起停都会振动，"停多久才算停稳"要实测（step-and-settle 那段停顿的长度）。
3. 哪一发对应哪个位置：两种都要验证（Rui 书面计划第 30 行），匀速扫靠时间或步数推算，step-and-settle 更直观。

## 5 两种方式的代价 [条件计算]
| | 匀速扫（停 0） | Step-and-settle（停稳暂按 1 ms） |
|---|---|---|
| 每个像素用时（像素 5 µm） | 1.25 ms | 走 1.25 ms + 停 1 ms + 打 125 发 1.25 ms ≈ 3.5 ms |
| 3 × 3 mm，像素 5 µm（不含每行开销） | 约 7.5 min | 约 21 min |
| 3 × 3 mm，像素 1 µm | 约 38 min | 约 3.75 h |
| 位置 | 每发位置不同，要推算 | 一个像素的 N 发在同一点 |
| 平均 | 平均的是一段像素宽度内的信号 | 同一点平均 |
| 电机 | 加速一次后匀速，振动小 | 每个像素起停，要等停稳 |
| 自由运行的激光 | 每发都用上 | 移动和停稳时的那些发浪费，但样品照样被照（Rui 计划 Notes 第 6 条） |
- 10/14 实测每行还有约 1.13 s 的固定开销（回程 + 软件），两种方式都有（docs/14 6.10）。

## 6 每个像素的 N 条：全部保留还是平均
| | 平均成一条 | 全部保留 |
|---|---|---|
| 信噪比 | 随机噪声降到约 1/√N（N = 125 约小 11 倍），只存平均值 | 原始数据都在，事后再决定怎么平均 |
| 3 × 3 mm 数据量 | 像素 5 µm 约 0.7 GB；1 µm 约 18 GB | 像素 5 µm 约 92 GB；1 µm 约 460 GB |
| 丢掉什么 | 单发之间的差别（激光能量起伏、像素内位置） | 不丢，但硬盘、存盘和处理时间都多 |
| 事后改像素 | 不能 | 能（重新分组） |
- 它决定的是：信噪比（图像噪声）、能不能事后改像素、数据量和存盘时间。**不决定扫描时间。**
- 建议（待用户确认）：测试和小扫描全部保留；大扫描边采边平均，把 N 写进参数。程序里用一个开关选。

## 7 用测试信号跑 100 kHz 的参数（草案）[条件计算]
| 项 | 值 |
|---|---|
| DO 时钟 fs | 200 kS/s（现在 248 kS/s） |
| 触发 P0.6 | 每 2 行一个 = 100 kHz，高电平 1 行 = 5 µs |
| STEP | 每 25 行一步 = 8 kHz = 4 mm/s（和现在一样） |
| 每个像素（DX = 5 µm） | 125 条 A-line |
| 2 mm B-scan | 400 像素 × 125 = 50,000 条，0.5 s，约 102 MB；板载内存约 65,536 条，装得下 |
| ATS | 每条 5.69 µs < 两次触发间隔 10 µs；每个 buffer 250 条 = 512,000 B = 125 × 4096；每秒装满 400 个 buffer（< 2000）。10/4 实测 100 kHz 下 1000 条不漏（docs/10） |

要先确认的（待实测）：
- **发生器**：现在 CH1 是 100 kHz 方波、Burst 1 个周期 = 10 µs，和触发间隔一样长，可能隔一个漏一个；可能要把 CH1 改成 200 kHz（一个周期 5 µs）。用示波器 + ctr1 对比 ATS 条数确认。
- **激光**：台上 NPL45C 手册最高 50 kHz（输入 0.2–2 V），100 kHz 不能用它；100 kHz 对应 Rui 计划里自由运行的 UV 激光（那时频率由激光定，P0.7 不用，光电二极管触发 ATS、计数器数脉冲）。
- P0.6 高电平只有 1 行（5 µs）时，发生器能不能稳定触发。

## 8 已经定的和还没定的
- 定了（用户 10/15）：代码要能在 100 kHz 下跑；按 Rui 的说法两种方式写成同一个通用表，"每个像素停多久"做参数，默认 0（匀速扫）。
- 建议、待用户确认：写 `bscan_test_100k.m` 草稿（原 bscan_test.m 不动）；全部保留 / 边采边平均做开关。
- 没定：每个像素平均几发；用哪台激光、多高频率；停稳时间什么时候测。

## 9 要问 Rui 的（下次见面或发消息时一起问；不用再问"两种方式有什么区别"，他已经答过）
1. **激光和频率** — 台上的 NPL45C 手册写最高 50 kHz，100 kHz 是指以后的 UV 激光吗？现在用 NPL45C 做真实信号时设多少？
   EN: The NPL45C on the bench is rated up to 50 kHz. Is 100 kHz meant for the UV laser later? What rate should I use with the NPL45C for real signals now?
2. **每个像素平均几发** — 我算了，100 kHz、4 mm/s 时像素 5 µm 每个像素有 125 发；3 × 3 mm 全部保留约 92 GB，平均后约 0.7 GB。我打算小扫描全部保留、大扫描边采边平均，想确认每个像素平均几发合适，或者有没有目标信噪比、像素大小。
   EN: At 100 kHz and 4 mm/s there are 125 pulses per 5 µm pixel. Keeping every A-line for 3 × 3 mm is about 92 GB; averaging gives about 0.7 GB. I plan to keep everything for small scans and average on the fly for large ones. How many pulses per pixel should I average, or is there a target SNR / pixel size?
3. **停稳时间** — 代码会把"每个像素停多久"做成参数，默认 0（匀速扫）。如果以后用 step-and-settle，停稳时间要实测，现在先不测可以吗？
   EN: The code will take "pause per pixel" as a parameter, default 0 (constant-speed scan). If we use step-and-settle later, the settle time needs to be measured. Is it OK to postpone that measurement?
